# Security policy

## Reporting a vulnerability

Please **do not** open a public issue for security problems. Report them privately
through the repository host's private vulnerability reporting (for GitHub: the
"Security" tab → "Report a vulnerability"), once the public repository is available.
Include what you found, how to reproduce it, and the version or commit you tested.

You can expect an acknowledgement within a few days. Please give us reasonable time to
fix the problem before you disclose it. We credit reporters who want to be credited.

## Supported versions

Only the latest release receives security fixes while the project is in version 0.x.

## How IDK Clips protects users

### Accounts and sessions (server and hybrid mode)

- Passwords are hashed with **Argon2id** (`argon2-cffi`, RFC 9106 parameters) and rehashed
  when parameters change. Unknown e-mail addresses take the same time to check as known ones.
- Sessions are random 256-bit tokens in an **HttpOnly, SameSite=Lax** cookie (Secure in
  production). Only a SHA-256 hash of each token is stored.
- **18+ and verified email are required.** Sign-up needs an explicit Yes to "Are you 18
  years of age or older?" (stored with a timestamp), and the address must be verified with
  a one-time code from Supabase Auth before any session exists. Codes expire, can be
  requested once a minute, and five wrong codes require a new one. The server re-checks
  both conditions on every protected request and for every worker request.
- **Password reset** uses a one-time code from Supabase's password-reset email (same
  expiry, cooldown and attempt limits), then logs the account out everywhere. Neither
  reset nor resend answers reveal whether an address has an account.
- Sign-in is throttled per account; sign-up, codes, uploads, processing and worker
  pairing are rate-limited. Repeated 401/403/404 answers slow a client down, request
  bodies are size-limited, and each user can have only a limited number of jobs waiting
  or running (with an optional daily processing quota).
- API responses carry `no-store`, `nosniff`, `X-Frame-Options: DENY`, a strict
  `Referrer-Policy`, `Permissions-Policy`, cross-origin isolation headers and, in
  production, HSTS. The website adds a Content-Security-Policy.
- Every state-changing request must carry `X-Requested-With: OpenClip` and an allowed
  `Origin`, on top of SameSite cookies (CSRF protection). CORS is an explicit allow list;
  wildcards are refused.
- **There is no administrator system**: no roles, admin accounts, admin endpoints or
  admin commands. Every account is an ordinary user. Sign-up, profile and settings
  requests with unknown fields (such as `role` or `is_admin`) are rejected (HTTP 422).
- Server-wide settings come only from the server's environment. Users choose their own
  AI provider and model, but never the address the server talks to (no SSRF through
  settings).
- Every query is scoped to the signed-in owner. Other users' projects, clips, jobs and
  workers answer "not found".

### Local mode

- There are no accounts, so the API **only accepts connections from this computer** (a
  loopback peer) and only with a `localhost`/`127.0.0.1` `Host` header, which blocks DNS
  rebinding attacks from websites.
- The server refuses to start on a network address in local mode.

### Workers (hybrid mode)

- Pairing codes are 8 characters from a 31-symbol alphabet, single use, valid for 10
  minutes by default, stored as hashes, and pairing attempts are rate-limited.
- Each worker receives its own 256-bit bearer token, stored only as a hash on the server.
  On the worker it is kept in `data/agent/credentials.json` (owner-only permissions on
  Linux/macOS; on Windows the folder's access rules apply). Revoking a worker makes the
  token useless.
- A worker can only claim jobs of its owner and only report results for the job it holds.
  Results are validated against strict schemas, size limits and storage-key rules.
- Workers accept a fixed list of job types and validate every value. There is no way to
  make a worker run commands.
- Workers connect outwards over HTTPS (plain HTTP is refused except for a server on the
  same computer). The server never connects to a worker.
- The worker's local bridge listens on `127.0.0.1` only, checks the `Host` header, allows
  only the paired website's origins, and requires a short-lived transfer token that it
  verifies with the server before reading or writing any file.

### Files

- Uploads are streamed to disk with size limits, checked with FFprobe (must contain video
  and audio), and never executed. File names from users are never used as paths.
- Storage keys are generated by the server and validated against path traversal.
- Imports from links block private, loopback and link-local addresses (re-checked after
  connecting and after every redirect) to prevent SSRF.

### Secrets and logs

- Configuration comes from environment variables or a local `.env` file that is never
  committed. External AI keys stay on the server.
- Logs redact configured secrets and never include passwords, tokens or video content.

### Content

- IDK Clips never downloads from YouTube or other platforms and contains no code that
  bypasses DRM or access controls (see `docs/YOUTUBE.md`).

## Checks we run

`ruff` (including security rules), `pytest` (authorization, cross-user isolation over every
route, no-admin, verification, pairing and upload tests), `pip-audit`, `npm audit`,
`detect-secrets` and a dependency license check, on every change in CI, plus GitHub
CodeQL and a daily scheduled audit. See `docs/TESTING.md`.

## Known limitations and remaining risks

No software is completely secure, and IDK Clips has not had an independent security audit.
Known limitations of the current release:

- On serverless hosting (the public website), rate limits and failed-login lockouts are
  kept in memory per function instance, so they are weaker than on a single server.
  Supabase's own limits apply on top, but Supabase sees the website's server address,
  not yours, so its per-address limits are shared by all users.
- The age check is a self-declaration (Yes or No); no identity documents are checked.
- The public website sends codes from a free-mail address without its own domain, so
  messages can land in spam, and DMARC protection against forged "IDK Clips" emails is
  weaker than with a dedicated domain.
- Deleting an account does not remove the email address from Supabase Auth's user
  record (see the privacy notice).
- There is no two-factor authentication; sessions last 14 days unless you log out or
  change your password.
- The Content-Security-Policy allows inline scripts, which the static Next.js export
  needs; React's output encoding, and documentation rendered at build time with raw HTML
  and active link schemes removed, are the main XSS defenses.
- Worker pairing relies on the browser's local-network permission to reach the worker
  bridge on `127.0.0.1`.
